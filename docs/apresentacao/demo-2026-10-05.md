## O que não demonstrar

Evitar durante a apresentação:

- tarefas antigas exclusivamente locais ou tentativa de migração de dados legados;
- exclusão/desfazer;
- filtros e ordenação ainda não concluídos;
- sincronização manual geral;
- CI;
- lembretes/notificações;
- login/autenticação real (a entrada atual é local).

São itens pendentes/futuros. Tarefas Front-only podem aparecer pelo AsyncStorage, mas não ter registro na API/SQLite para mutações remotas; reconciliação pertence à #12.

## Plano B — Se o emulador/API falhar

1. Não entrar em pânico nem reinstalar nada. Manter os dados e conferir os terminais.
2. Verificar o dispositivo:

   ```sh
   adb devices
   ```

3. Verificar Metro:

   ```sh
   curl http://localhost:8081/status
   ```

4. Verificar backend:

   ```sh
   curl http://localhost:3000/health
   ```

   Porta padrão **3000**, confirmada em `backend/src/config/env.ts`, `backend/.env.example` e no cliente mobile. Se o ambiente local definir `PORT`, usar a porta efetiva exibida pelo backend e verificar compatibilidade com o cliente; não alterar configuração durante a demo. Esperado: HTTP 200, `{"status":"ok"}`.

5. Se o emulador não abrir, utilizar o AVD existente:

   ```sh
   ~/Android/Sdk/emulator/emulator -avd Pixel_7 -no-snapshot-load
   ```

   Não abrir outra instância se a anterior ainda estiver ativa.
6. Se houver problema de renderização, utilizar a alternativa já conhecida de renderização por software do AVD somente se necessário, sem wipe de dados. [Registro anterior](../arquitetura/integracao-status-historico.md#android--validação-manual-via-adb). O registro não especifica uma flag; não improvisar configurações novas na apresentação.

Se uma ferramenta local continuar falhando, seguir pela arquitetura, documentação, evidências dos PRs e explicação dos fluxos. Distinguir resultados previamente validados de uma demonstração ao vivo indisponível; não declarar sucesso ao vivo sem observá-lo.
